**CHALK traversal review and surface/capability proposal**

Reviewed September 14, 2026 Toronto time / September 15 UTC. Audience: user and Claude Opus 5, the implementing agent. This is a read-only code/log review and proposed next work, not a gameplay implementation.

**Recommendation**

Keep the shared traversal executor. Add an explicit, reusable surface-data provider and a candidate evaluator that combines the object's usable contacts, the character's learned abilities/current condition, actual geometry and animation fit. Use GAS tags to describe capabilities, temporary opportunities and active actions as distinct concepts. Grant core traversal abilities once; do not grant and revoke them every time the character approaches a fence.

The desired human-like decision is: **I know this action; this surface offers suitable contacts; I can reach and finish it from here; I choose to do it.** A deterministic evaluation can represent those factors without requiring a learned AI model.

**Current implementation: retain these foundations**

- Mantle, hurdle and climb have thin wrappers using UAZ_GA_Traversal/FAZ_TraversalRequest, sharing target registration, Traversing mode, root-motion execution and teardown.
- Requests include a nonzero montage entry time. Selection now considers measured remaining approach, foot preference and style preference; no-input entry is separated from residual speed.
- Hurdle measures a far edge and landing; climb has a separate height band. Current native defaults cover mantle 75–125 cm, hurdle up to 110 cm with its other gates, and climb 205–285 cm. The intervening unsupported height range is an animation/coverage limit, not something a tag fixes.
- Distinct Started/NoCandidate/BodyBusy results replace the earlier boolean ambiguity.
- FullBody and Traversing keep ordinary jump-landing animation out of traversal completion, and AnimInstance guards preserve the traversal root-motion drive while the mode is active.
- Logs show successful mantle, hurdle and climb and consecutive action activations. This proves the actions run; it does not prove intentional input buffering, smooth pose transitions, network correctness or complete failure recovery.

**Proposed architecture: world data + capability + current opportunity + execution**

The following names are illustrative new design, not existing implemented tags/classes.

| Layer | Example | Ownership/lifetime |
|---|---|---|
| Learned capability | Capability.Traversal.Climb; granted GA_Climb | Character progression/loadout; persists until genuinely lost |
| Surface description | Surface.Type.Fence; Surface.Traversal.Grippable; Surface.Traversal.NoTopStanding | Actor/component/profile, not the character ASC |
| Current opportunity | Traversal.Available.Climb with a validated candidate handle | Evaluator; short-lived, changes with position/geometry |
| Active action | Existing State.Traversing plus action ID/type | Executor; retained through the committed action and cleared by its owner |

1. Add a portable UAZ_TraversalSurfaceComponent or equivalent explicit interface. It supplies allowed action families, contact edges/points, usable widths/depths, direction restrictions, grip/support traits and optional profile overrides. Static world props do not each need an AbilitySystemComponent.
2. Keep an adapter for existing GASP authored splines. Add simple procedural/baked box-edge support where bounds and collision make that valid. Add generic collision-derived geometry later behind the same interface. Bounds are a candidate source, not proof of a clear path or grippable fence.
3. Reuse profiles across a mesh/prefab family, with per-instance overrides. For existing StaticMeshActors, permit an instance component or a separate registered annotation volume linked explicitly to the hit mesh/component. A nearby marker without a resolver must not silently claim arbitrary objects. Preserve a target/component/instance identity for streamed and instanced content.
4. Build candidates on demand and optionally refresh nearby opportunities for UI/anticipation. Filter impossible options first: missing capability, prohibited surface, missing contact/path/support, missing animation coverage, incompatible current action. Rank the remaining options by intent/facing, approach distance, pose/foot compatibility, required warp distortion and recovery fit.
5. Store actual geometry in a candidate struct: actor/component, surface ID/revision, local/world anchors, predicted destination, action, selected montage/start time, measured support, expiry and rejection reason. A tag cannot hold this information. Prefer a stable candidate with hysteresis to per-frame action flicker; revalidate immediately on commitment and after preparation such as holstering.
6. On explicit input, invoke the chosen existing ability with that candidate through an appropriate GAS request/target-data route. Validate on authority where networking applies. Keep candidate availability separate from the active action: the character moving away from the original approach point must not remove a ready tag and cancel its own climb.

**How dynamic GAS tags should work**

Yes, availability tags can be added/removed dynamically, and GAS supports tag-triggered abilities. Epic distinguishes GameplayEvent, OwnedTagAdded and OwnedTagPresent triggers. The local engine header specifies that OwnedTagPresent cancels when its tag disappears. That is useful for some persistent conditions, but a poor binding for a committed climb whose proximity tag naturally disappears as it moves. [Epic trigger API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/EGameplayAbilityTriggerSource__T-), [C:/UnrealEngine/Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Public/Abilities/GameplayAbilityTriggerType.h:20](C:/UnrealEngine/Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Public/Abilities/GameplayAbilityTriggerType.h:20).

Recommended use: tags advertise/gate an opportunity; input commits a validated request with a payload. Never start every newly available movement automatically merely because the character approached a surface. Ready tags should have a single scoped writer or owned effect/count handles, update on changes, and be removed only by their owner. Actor Tags (FName) are not automatically Gameplay Tags on an ASC; explicitly expose/copy surface tags into the evaluator/request.

Grant mantle/hurdle/climb at startup or when the character learns them. Grant tool-specific movement when the loadout provides it, with an explicit removal/cancellation policy. Proximity usually changes availability, not what the character has learned. Epic documents server-owned ability granting/revocation and activation requirements separately. [Epic ability lifecycle](https://dev.epicgames.com/documentation/unreal-engine/using-gameplay-abilities-in-unreal-engine).

**Smart Objects and alternatives used in games**

- **Authored contacts plus contextual animation:** GASP demonstrates choosing montage/entry frames using gameplay context, Choosers and Motion Matching. Its traversal gameplay is deliberately a simple example. This supports retaining its animation techniques while improving AZ's provider and action contracts. [Epic Game Animation Sample](https://dev.epicgames.com/documentation/unreal-engine/game-animation-sample-project-in-unreal-engine).
- **Broader geometry interaction plus authored special interactions:** Guerrilla describes Horizon Forbidden West's climbable rocky areas without the first game's tribal handholds, high vaults onto reachable objects with room to pull up, and authored grapple points. This is an example of combining several traversal mechanisms. The article documents player-facing design, not the internal detection algorithm; the proposed AZ hybrid is our design inference. [Guerrilla on PlayStation Blog](https://blog.playstation.com/2021/10/25/horizon-forbidden-west-master-aloys-new-abilities/).
- **Reservation-based smart interactions:** Unreal Smart Objects attach reusable definition data and slots to actors, support spatial/tag-filtered discovery and claims, and require cleanup on completion/abort. Execution remains with the interactor. They fit shared ladders, narrow fence-crossing spots, boosts, doors or interactions where two characters must not use the same location simultaneously. They do not supply animations or solve arbitrary mesh collision. [Epic Smart Objects overview](https://dev.epicgames.com/documentation/unreal-engine/smart-objects-in-unreal-engine---overview).

For CHALK, use the lightweight surface provider/evaluator as the base and add Smart Object slots selectively where reservations or scripted roles are useful. Requiring a Smart Object on every curb would add authoring and integration work without solving the main current gaps. A pure tag-only system is too little geometry; a fully generic physics-only system cannot infer grip safety, barbed wire or narrative restrictions. A hybrid combines reusable semantic profiles, derived geometry and explicit overrides.

**Dynamic transitions between actions**

Separate three concepts: selecting the next legal action, blending the current action into locomotion, and deliberately chaining two traversal actions. The current code does the first on input and can activate consecutive actions; it has no complete transition graph for arbitrary parkour chains.

Maintain one active committed action and, optionally, one prospective next candidate. Choose successors using the actual exit pose/velocity/support and current intention. Commit a new action only at a validated transition boundary with the input policy explicitly satisfied. Never change an in-flight mantle into a climb merely because a new availability tag appears. Preserve tap-once input now; an intentional hold-to-parkour mode would be a separate design feature, not accidental retries from Held input.
