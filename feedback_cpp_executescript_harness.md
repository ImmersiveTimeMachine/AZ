`mcp__unrealclaude__unreal_execute_script` with `script_type=cpp` is a live one-off C++ runner — far more powerful than I assumed. Verified by reading the plugin (`ScriptExecutionManager::ExecuteCpp`, 2026-06-14).

**How it works:** It writes `script_content` **verbatim** (no wrapping/template) to `C:\UnrealEngine\Games\AZ\Source\AZ\Generated\UnrealClaude\<sanitized-@Description>_NNN.cpp`, then triggers `LiveCoding.Compile` on the whole AZ module. There is **NO entry-point call** — nothing invokes your code. So your code MUST run from a **file-scope static initializer** (a `static` object whose constructor does the work; Live Coding runs it when it patches the new TU in).

**Why it's worth it:** the constructor runs as normal editor game-thread code with full access — `LoadObject`, reflection (`FindPropertyByName`/`FScriptArrayHelper` reach PRIVATE members like `UPoseSearchDatabase::DatabaseAnimationAssets`), direct access to protected fields C++-side (`UAnimSequence::Notifies`), and calling AZ statics (`UAZ_PoseSearchUtils::*`). This is how to read/mutate things Python can't (Python reported `Notifies` / `DatabaseAnimationAssets` as protected/unreadable). **No new UFUNCTION, no editor restart** — unlike adding methods to a util class.

**Template (use this shape):**
```cpp
// @Description: AZ_ascii_only_name_no_punctuation
#include "CoreMinimal.h"
#include "UObject/UnrealType.h"   // FArrayProperty / FObjectProperty / FScriptArrayHelper
// ... other engine + AZ headers ...
namespace {                       // anonymous ns = internal linkage = no cross-run dup-symbol clashes
  struct FRun { FRun() { /* work here; UE_LOG(LogTemp, Warning, TEXT("AZCPP ...")) */ } };
  static FRun GRun;
}
```
Filter output with a unique tag (e.g. `AZCPP`) via `unreal_get_output_log filter=AZCPP`.

**TRAPS (all hit on 2026-06-14):**
1. **ASCII-only @Description.** A non-ASCII char (em-dash `—`) became the filename; UBT recorded it in a different encoding than NTFS wrote → `C1083 Cannot open source file` that **persists in the cached makefile and fails EVERY later compile**. Fix: `rm` the phantom `.cpp` AND `rm Intermediate/Build/Win64/x64/AZEditor/Development/Makefile.bin`, then write a FRESH script (a *changed source* — see #2).
2. **Console `LiveCoding.Compile` alone won't re-run after only deletions.** Live Coding compiles only on a *changed/added source file*; deleting files is not a trigger. To force a clean rebuild after fixing the dir, submit a new `cpp` script (new file).
3. **Anonymous namespace is mandatory** if you run multiple cpp scripts in a session — each generated `.cpp` stays in the module; same-named file-scope symbols across TUs = duplicate-symbol link errors. Anon ns gives each its own.
4. **Clean up after.** `rm Source/AZ/Generated/UnrealClaude/*.cpp` when done — else they recompile and their static initializers RE-RUN on the next editor-start build. (A plugin `cleanup_scripts` tool also exists.)
5. **NEVER save / do editor-init-dependent work in the static init — it CRASHES editor STARTUP.** Confirmed 2026-06-22 (`FEditorFileUtils::PromptForCheckoutAndSave`) and **REPEATED 2026-07-18** (`UPackage::SavePackage` building BT assets — the leftover TU got ingested by the user's next full build; every editor launch then crashed in `CallPreSave → IndexToObject` during `FEngineLoop::LoadStartupModules`). The static init runs at MODULE LOAD (PreInit on full-build startup; patch-apply on Live Coding) — only do reflection/`LoadObject`/in-memory mutation there; mark dirty and save AFTERWARD via python `EditorAssetLibrary.save_loaded_asset` or unreal-mcp `AssetTools.save_assets`. Also: Live Coding may NOT compile a brand-new generated file mid-session (observed both ways — the 2026-07-18 BT script silently no-op'd in-session, then detonated via the full build) — treat "task queued but no log output" as NO-OP + LIVE BOMB ON DISK.
   **MANDATORY MITIGATIONS (2026-07-18):** (a) EVERY harness script's ctor starts with `if (!GIsRunning) { return; }` — makes any leftover TU inert at boot (GIsRunning is false during PreInit, true when a Live-Coding patch applies in a live editor); (b) delete the generated TU IMMEDIATELY after the task completes — before ANY build can run, not "at session end"; (c) never SavePackage in the init. **Recovery recipe:** `rm Source/AZ/Generated/UnrealClaude/*.cpp` → CLI Build.bat (relinks without the TU, ~5 s) → also DELETE any asset the boot-time init created (born at PreInit = untrustworthy) → editor launches again.
   **THIRD OCCURRENCE 2026-07-21 (BT_Chalkie crowd-brain fork) — cost 3 editor crashes.** All three mitigations were skipped because the harness was written from MEMORY.md's one-line summary, not this file. New standing rule: **READ THIS FILE IN FULL before every cpp-harness use — the summary line does not carry trap #5.** Extra findings this round: (i) a leftover TU whose init MUTATES loaded assets in memory (no save) is also a boot-killer when combined with `OpenAssetsAtExit` editor-restore — startup order is module-load init → RestorePreviouslyOpenAssets → BT editor opened over the mutated/graph-nulled asset → SpawnMissingNodes crash; unblock by removing the asset's `OpenAssetsAtExit=` line from `Saved/Config/WindowsEditor/EditorPerProjectUserSettings.ini`; (ii) a PreInit-run `UPackage::Save` crashes AFTER the file is fully written (`PostSavePackage → DataValidationModule → GetSubsystemInternal` on an uninitialized subsystem collection) — the saved uasset itself can be intact (verify content by binary grep / structural dump before trusting OR discarding it); (iii) BT-editor graph regen from a runtime tree is real (`BTGraph=nullptr` → open → `SpawnMissingNodes`) but the tree must have NO empty child slots (null ChildComposite+ChildTask → `FindGraphNodePin(null)` crash) and the asset MUST be saved with the BT editor CLOSED.
   **FINAL VERDICT 2026-07-21 (fourth failure): the BTGraph=nullptr technique is NOT ROUND-TRIP SAFE — never use it again.** The regen LOOKS right and even PIEs right in that session, but the regenerated graph is not equivalent to a hand-built one: the next BT-editor save (or a fresh-session reload of the package saved that way) rebuilds/loads the runtime tree EMPTY — root selector, zero children — silently gutting the asset. Binary-grep of node-name strings is NOT proof of a healthy tree (orphaned exports keep their names); verify by walking RootNode children in a FRESH session. Programmatic BT structure edits are effectively banned until a proper editor-module tool exists (AZEditor module + BehaviorTreeEditor dependency, driving the same code paths as the BT editor UI); until then BT structure = HAND-EDIT ONLY (the original standing rule, now proven at the cost of ~4 crashes + 2 git restores in one evening). Value-only tweaks on existing nodes (floats, key bindings via python set_editor_property) remain fine.

Read compile result from `C:/UnrealEngine/Engine/Programs/UnrealBuildTool/Log.txt` (`Result: Succeeded` / `error C####`); `.voltbl` warnings in LiveCodingConsole.log are non-fatal. Saving from the static init is risky — prefer marking dirty in cpp and saving via Python `EditorAssetLibrary.save_loaded_asset(obj, only_if_is_dirty=False)` (note: `save_asset(path,...)` returned False for PSD/anim here — use `save_loaded_asset`).
