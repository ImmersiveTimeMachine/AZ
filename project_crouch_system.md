Two-tag-space design (see [[project_v2_architecture]]): `Movement.Crouching` (GAS intent, ASC/game-thread) vs `Mover_IsCrouching` (Mover sync-state RESULT, rollback-aware, on proxies). ## ★ The crouch SPIKE — root-cause analysis (✅ FIXED via option A; see the "option A FIXED & VALIDATED" bullet further down — this section is kept as the diagnostic history, incl. the early WRONG model that the interpolated sim-proxy was the popping view)
Symptom: ~35cm one-shot vertical POP at crouch/uncrouch on SMOOTHED remote views. **Engine limitation, NOT our bug.** (NOTE: the "Phase 2 options" below are historical — option 2, the teleport-flag, is exactly what shipped as "option A". The reusable doctrine still holds.)
- **Cause:** `AdjustCapsule` (`StanceModifier.cpp:218-232`) queues a capsule-down `FTeleportEffect` (a SIM effect) AND slams the mesh-up offset INSTANTLY (`SetBaseVisualComponentTransform`). Atomic on the owner (one sim frame, net zero). On an **interpolated** sim proxy, `TickInterpolatedSimProxy` runs `OnStart` (`MoverComponent.cpp:498`) → instant mesh-up, but the capsule-down only arrives via **interpolated** replication (`:423`, `BaseVisualComponentTransform * interpolated ActorTransform`) → lags → mesh pops up then settles.
- **`bSyncInputsForSimProxy=true` is already set in the pawn BP** — it makes the proxy ANIMATE crouch (input→GetLastInputCmd for anim) but does NOT fix the spike (`OnPreSimulate`/`TickInterpolatedSimProxy` paths, `MoverComponent.cpp:431,890`). It's also the fix for the proxy "idle while moving" bug (bIsMoving/Gait input-derived).
- **No built-in param fixes it.** Checked: `SmoothingMode` (only `None`|`VisualComponentOffset`; None = choppy proxies, not a fix), `UStanceSettings` (no transition field), no teleport-snap toggle. The proxy snap is a hardcoded **500cm distance heuristic** in `FMoverDefaultSyncState::Interpolate` (`MoverDataModelTypes.cpp:289`) — our 35cm never trips it. Epic has a literal TODO there to "replace this threshold with a flag."
- **THE TWO-TIER PRINCIPLE (reusable doctrine):** Mover state splits into *interpolated sim state* (transform — lerped by ONE shared alpha across the whole sync-state collection, `FMoverDataCollection::Interpolate`, MoverTypes.h:307) and *discrete side-effects* (modifier OnStart/OnEnd, instant effects). Side-effects are atomic with the transform ONLY on the simulating machine. **Any visual quantity that must stay coupled to the interpolated transform must itself live in the interpolated sync state, never be applied as a side-effect.** FStanceModifier violates this → why it only breaks on proxies.
- **Phase 2 options (do at MP polish, fix lives in OUR AdjustCapsule):**
  1. **Structural (correct, smooth):** `FAZ_StanceVisualState` — a custom `FMoverDataStructBase` carrying the offset in the sync state, `Interpolate` lerps it by Pct → locked to the root's alpha → net zero at every step. Project-side (custom struct + component drives BaseVisualComponentTransform from the interpolated value) — no engine edit but real work (rollback/merge/decay paths too).
  2. **Teleport-flag (lighter, 1-frame snap):** implement Epic's TODO — add `bSkipInterpolation:1` to `FMoverDefaultSyncState` (+NetSerialize +honor in Interpolate), set it in `FTeleportEffect::ApplyMovementEffect` (general) or opt-in per teleport. Core-engine-struct patch (carried — see [[project_local_plugin_patches]]). Fixes ALL sub-5m teleports on proxies.
- **DECISION (2026-06-08): tried option 1 (structural B-full), then REVERTED to clean Phase 1.** B-full (interpolated `FAZ_StanceVisualState` sync-state struct + Walking-mode writer + `OnMoverPostFinalize` reader + AdjustCapsule suppress) proved too fragile — every per-role timing tweak regressed another role (proxy-fixed↔owner-broke↔both-broke across ~5 build cycles). For a remote-proxy-only COSMETIC issue on an SP-first project, not worth it. **Reverted: deleted `AZ_StanceVisualState.*`, removed the writer + reader + their decls/includes/fields; `FAZ_StanceModifier::AdjustCapsule` = plain `Super` (Phase 1).** Current state = engine-native crouch: **owner/local view CLEAN, remote sim-proxy pops** (the original known-good baseline). `FAZ_StanceModifier` (the custom modifier, Phase 1) is KEPT and confirmed live.
- **★ LESSONS from the B-full detour (keep):** (a) modifiers CANNOT write sync state (callbacks are `const FMoverSyncState&`) — only modes/effects can. (b) `FMoverDataCollection::Interpolate` DOES interpolate every struct in the collection (`MoverTypes.cpp:299`), not just registered ones; `OnPostFinalize` fires on interp proxies with the interpolated state — so the sync-state-struct approach is mechanically sound, it's the cross-role TIMING that's the trap. (c) `BaseVisualComponentTransform` is the mesh's FULL authored relative transform (e.g. -90, set in `UMoverComponent::SetPrimaryVisualComponent` `:2188`), NOT a bare delta — apply `base + delta` or the mesh flies up ~90cm. (d) the owner/authority/autonomous are NOT interpolated, so the engine's instant offset is fine there; only the interp sim-proxy needs help.
- **★ GAS↔Mover desync FOUND (separate latent bug):** `UAZ_PawnCameraMovementComponent::TickComponent` (`AZ_PawnCameraMovementComponent.cpp:113`) reads the **GAS** tag `ASC->HasMatchingGameplayTag(Movement.Crouching)` for the crouch camera framing, while body/capsule/anim read the **Mover** result `IsCrouching()`. Two replication channels, two clocks → camera can lead/lag the body. The camera InterpTo's (eases, doesn't snap) so it's not the sharp mesh spike, AND there's no camera on replicas — but it VIOLATES the v2 doctrine (visuals derive from the Mover result, not GAS intent). **Fix (deferred, correctness):** point line 113 at the Mover `IsCrouching()` (needs the CharacterMoverComponent ref) instead of the ASC tag.
- **PROXY POP — option A ✅ FIXED & VALIDATED 2026-06-08 (engine/Mover patch).** Root cause: crouch re-centers the capsule by the half-height delta (StandingHH 90 − CrouchHH 55 = **35cm**, the "±30-40" the user measured — UE capsules are CENTER-anchored, so a shorter capsule must drop its center to keep feet planted); the mesh offset is applied INSTANTLY but the re-center reaches SMOOTHED views lagged → ±35 pop. **The popping view is NOT the interpolated sim-proxy** (that was smooth) — it's the **listen-server's view of a REMOTE client** (role=Authority on the server, sub-tick smoothed). CMC solves the identical case explicitly (`CharacterMovementComponent.cpp:3342-3351`, comment "Don't smooth this change in mesh position", fires for `ROLE_SimulatedProxy` AND `IsNetMode(NM_ListenServer) && RemoteRole==AutonomousProxy`). Mover lacked the guard. **Fix = engine patch, ZERO AZ-side changes** (crouch already queues FTeleportEffect via AdjustCapsule→Super; the patch makes that teleport SNAP not lerp): (1) `uint8 bSkipInterpolation` on `FMoverDefaultSyncState` (`MoverDataModelTypes.h`); (2) serialize it in `NetSerialize`; (3) `Interpolate` snaps (`*this=*ToState`) when `ToState->bSkipInterpolation` (implements the engine TODO); (4) `FTeleportEffect::ApplyMovementEffect` sets it after `SetTransforms_WorldSpace`. Naturally one-shot — the sim builds a fresh sync state each tick.
  - **★★ THE BUG THAT MADE IT A NO-OP FOR TWO BUILDS (critical lesson):** my first cut ALSO cleared the flag in `SetTransforms_WorldSpace` (intending one-shot). But the movement mode's **floor-snap calls `SetTransforms_WorldSpace` again right after the crouch teleport** → wiped the flag before it replicated → patch had zero effect even though Mover was confirmed-rebuilt. **DO NOT clear `bSkipInterpolation` in `SetTransforms` — anything that re-sets position after a teleport eats it.** Removing the clear = the fix. (Diagnosed via a temp `UE_LOG` in `Interpolate` that never fired → flag wasn't reaching the path → it was being cleared upstream.)
  - **BUILD GOTCHA:** an engine-plugin struct-layout change (adding the member) CANNOT be Live-Coded and the **Mover module must actually recompile** — a partial/LC build silently leaves the old `UnrealEditor-Mover.dll` → "no effect." Verify via the DLL timestamp. Full editor-closed `Build.bat AZEditor` rebuilt 3124 actions (~18 min, the struct ripples everywhere). NetworkPrediction (sync) path only — Chaos async (`ApplyMovementEffect_Async`) would need the same line if ever switched.
  - **Tracked:** patch file `docs/engine-patches/mover-crouch-skipinterp.patch` (in AZ repo) + [[project_local_plugin_patches]] #5. The 3 Mover files are ALSO modified-tracked by the separate engine repo at `C:/UnrealEngine` (the game repo is `C:/UnrealEngine/Games/AZ`).

## ★ STANCE TRANSITIONS (Idle2Crouch / Crouch2Idle) — DONE + working 2026-06-09
Plays a dedicated lower/rise clip on a stance change while idle. **Design decision (defended vs the user): ONE generic `TransitionStance` enum value, NOT per-target `TransitionToCrouch`/`TransitionToStand`.** Rationale: (a) crouch is ORTHOGONAL to the movement-phase axis — the `TransitionTo*` values name destination movement phases (Idle/Loco/Air loops), but you stay *idle* through a stance change, only the Stance dimension flips; `TransitionToCrouch` would mis-file it as a peer phase. (b) Scales without enum growth — the chooser keys the clip off the (target) Stance column; 3+ stances (prone) just add a `PreviousStance` chooser column once, vs per-target which grows the enum AND needs that column anyway. Tradeoff: read SMState+Stance together to know direction (the chooser does anyway).
- **Build (committed):** `EAZ_StateMachineState::TransitionStance = 9` (appended — enum is an ABI w/ the chooser, never renumber). `ComputeNextState`: `IdleLoop`(default) + `IdleBreak` cases detect the stance edge → set TransitionEndTime placeholder → return TransitionStance; new `case TransitionStance` holds on the timer → IdleLoop. AnimInstance: `TransitionStance` added to `bInTransition` (gets the clip-lock + `NotifyTransitionClipPushed` → real clip length) but EXCLUDED from the RM queue via `bInPlaceStanceTransition` (in-place — capsule already resized by the engine stance modifier; do NOT add it to `IsTransitionPhase`, no RM move = nothing to teardown). Chooser rows 52/53: `(TransitionStance, Crouching)→Idle2Crouch_new`, `(TransitionStance, Standing)→Crouch2Idle_new`, Gait/Dir/StartDir should be **Any** (user initially set Walk/F/Fwd Equal — Gait=Walk is a real over-constraint: run-held crouch would miss the row; loosen to Any).
- **★ Deferred-edge fix (the subtle one):** the stance edge `In.Stance != PreviousStance` was a ONE-FRAME signal because `PreviousStance` updated every `Tick`. If the flip landed in a state that doesn't check it (stop/start/air) the edge was eaten → crouch-mid-stop finished the stop then SNAPPED to crouch-idle, skipping Idle2Crouch. **Fix: `PreviousStance` now tracks the LAST SETTLED/SHOWN stance, not last tick** — removed the unconditional write at `Tick` (was line 68); now written ONLY in the moving branch top, air branch top, and the TransitionStance→IdleLoop settle. Idle/break/stop deliberately DON'T write it, so a crouch pressed mid-stop persists until IdleLoop and fires there. Subtlety that makes the moving-frame write essential: crouch-WHILE-walking → stop must NOT replay Idle2Crouch (you're already low) — the moving frames consume the change so post-stop sees `Crouching==Crouching`. LC-safe (moved an existing member assignment, no reflection).
- **Optional interrupt (offered, user's call):** add the same `In.Stance != PreviousStance` check at the TOP of the `TransitionToIdle` case → crouch CUTS the stop short and plays Idle2Crouch immediately (responsive) instead of waiting the full stop. The edge is available there because the stop doesn't write PreviousStance. Recommended for feel; the 0.2 blend hides the cut.

## ★ BlendOut field (outgoing-wins) — IMPLEMENTED, PENDING BUILD+PIE 2026-06-09
Lets a transition clip own its blend-OUT independent of the target loop's blend-in. **Mechanism reality:** a BlendStack has ONE crossfade per push (incoming's BlendTime drives it; a clip's "blend out" is just the next clip's blend-in) — so you can't sum out+in (that's one longer ramp; sequential would dip/hitch). **Outgoing-wins override:** `FAZ_ChooserOutputs::BlendOut` (new reflected field, default 0 = no override → existing rows unaffected) + `UAZ_MoverAnimInstance::PendingBlendOut` (one-shot stash). In `SetBlendStackAnimFromChooser`: `Crossfade = (PendingBlendOut>0) ? PendingBlendOut : ChooserOut.BlendTime`; both push paths use `Crossfade`; after the committed push `PendingBlendOut = ChooserOut.BlendOut`. Placed AFTER all no-push early-returns so it survives the held transition until the clip is actually replaced. So Idle2Crouch blends in over BlendTime, out over BlendOut, regardless of the crouch-idle row's 0.75 — while a stop still settles into that idle over 0.75. **Needs a full editor-closed AZ build (reflected struct field).** After build: `set_cell_output_struct_field_on_sub(path,"",row,10,"BlendOut","0.3")` on rows 52/53; tune. Use `max(out,in)` only if a too-fast BlendOut ever pops the incoming clip.

Binary state: crouch loco rows + stance transitions (`TransitionStance=9`) are BAKED + PIE-working. The **BlendOut field is uncommitted-uncompiled** — next build picks it up (then set rows 52/53 BlendOut + PIE).
